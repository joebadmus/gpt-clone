# SA-1275: Load testing: build a dashboard for the SAYT UI and its backend services

**Epic:** SA-962 (load testing)
**Suggested labels:** SAYT public test, monitoring
**Assignee:** Joe
**Depends on:** SA-1274 (agreed approach)
**Related:** the SAYT UI dashboard and service reliability dashboard tickets from the 16 Nov logging plan, if they've been raised. Check with Dan and link them rather than duplicating.

## Description

We need to watch the system while the load tests run, so we can see where it slows down or fails. Matt shared last year's dashboards in the `survey-assist-sandbox` project. They were built in sandbox only, weren't version controlled, and use the old service names.

This ticket builds a load testing dashboard for the SAYT UI and the services behind it. It starts from last year's dashboards and is built in sandbox first. It's kept as code so it can be applied to pre-prod for the final run (SA-1280).

If the SAYT UI dashboard or reliability dashboard from the logging plan is already in progress, extend it with the load testing panels below, rather than making a separate dashboard.

## Approach

1. Review last year's sandbox dashboards and keep the useful panels.
2. In the `survey-assist-sandbox` console, build a dashboard with:
   - **Traffic:** requests per second, by service and by UI page.
   - **Errors:** 4xx and 5xx counts and rates, by service.
   - **Latency:** p50, p95 and p99 per UI page (from load balancer logs) and per service.
   - **Cloud Run saturation:** instance count, concurrent requests per instance, CPU and memory, and cold starts or startup latency.
   - **Backends:** latency and errors for the Survey Assist API, the vector store on GKE (pods, CPU and memory, restarts) and the OTP verification service.
   - **LLM:** Vertex AI or Gemini request count, errors and 429 (quota) responses, if the journey calls them.
   - **Cloud Armor:** allowed and blocked requests, so we spot it blocking the test.
3. Use the log analytics bucket where it helps. It already exists for SAYT in sandbox, dev and pre-prod.
4. Export the dashboard JSON into the Terraform repo, with the project ID and service names templated, following the dashboards-as-code pattern agreed on 16 Nov.
5. Apply it to sandbox through the pipeline. Plan it for pre-prod (needed for SA-1279 and SA-1280).
6. Do a quick check by running a few manual journeys and confirming the panels show data.

## Things to be aware of

- Some panels depend on application logs from the SAYT UI (Steph's logging work). Note any panel that can't be built yet.
- Keep it focused on load testing. The wider API usage and security dashboards are separate tickets.
