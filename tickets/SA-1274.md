# SA-1274: Load testing: review last year's setup and agree the approach with Geoff

**Epic:** SA-962 (load testing)
**Suggested labels:** SAYT public test
**Assignee:** Joe, working with Geoff Henderson
**Related:** SA-1139, SA-1140, SA-1141, SA-1142 (Locust suite), SA-1143 (initial load test and documentation)

## Description

The SAYT UI Locust suite is nearly ready. SA-1141 and SA-1142 are in review. Once they're merged, the suite runs the full survey journey from start to finish, logging in with one-time access codes from a CSV.

Geoff moves to other work from early December. Before then, Joe is taking on the infrastructure side of load testing: the dashboards, getting the environments ready, running the tests with Geoff, and tuning the infrastructure if problems show up.

Last year's load testing material (dashboards, results and docs) is spread across several places. This ticket is for going through it with Geoff and agreeing how this year's tests will run, so the tickets that follow (SA-1275 to SA-1280) start from a shared plan.

## Approach

1. Geoff gathers last year's material into one place: dashboards, results, Confluence pages and the Locust docs from SA-1143.
2. Hold a walkthrough session covering the Locust suite, how to run it, the CSV of access codes, and how to read the output.
3. Agree the test scenarios:
   - **Realistic:** about 50 concurrent users with realistic think times. 50 is the record figure. Steve's minimum benchmark is 25 concurrent users.
   - **Stress:** think time set to zero, ramping up until latency or errors break the limits.
4. Agree pass/fail limits with Matt and Steve, for example p95 latency per page and the maximum error rate at 25 and 50 users.
5. Agree where Locust runs from (a laptop, a VM or Cloud Run) and what IP its traffic comes from. Check one machine can drive 50 or more users.
6. Confirm whether the journey calls Vertex AI or Gemini, and roughly how many calls each survey makes. This affects cost and quota (see SA-1276).
7. Confirm the environment order Matt agreed:
   1. Sandbox exactly as it is now.
   2. Tune and repeat.
   3. Final run in pre-prod with production settings.
8. Write it all up on the load testing Confluence page, using the run template from SA-1143 if it's ready.

## Things to be aware of

- Every journey uses up an access code, so the number of codes needed depends on the users and the length of each run.
- Don't duplicate SA-1143. This ticket agrees the approach, and SA-1143 owns the run template and documentation.
- SA-1158 (API load test plan) is separate and isn't covered here.
