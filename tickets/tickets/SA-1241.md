# SA-1241: Add ONS VPN IPs to GKE control plane whitelist

## Description

The GKE clusters in sandbox and preprod only allow control plane access from IPs on an allow-list. The ONS VPN IPs aren't on it yet, so ONS-managed laptops can't reach the cluster with `kubectl`.

The allow-list is held outside Terraform, in a secret per environment in the CI/CD project. Terraform reads the latest version and applies it to the cluster. So this is a manual secret update followed by a Terraform apply. No code changes.

The three ONS VPN IPs are already in the Cloud Armor allow-list secret, so we copy them from there.

| | Sandbox | Preprod |
|---|---|---|
| Allow-list secret (in `ons-cicd-surveyassist`) | `sandbox-gke-master-whitelist-cidrs` | `preprod-gke-master-whitelist-cidrs` |
| Cluster | `survey-assist-sandbox-cluster` | `ons-survey-assist-preprod-cluster` |
| Terraform folder | `survey-assist-sandbox` | `ons-survey-assist-preprod` |

Source of the VPN IPs: regional secret `cloud_armor_ip_allow_list` in `ons-cicd-surveyassist` (europe-west2).

NatCen also has a GKE cluster but is out of scope here, because NatCen applies are on hold until their testing ends.

## Steps

Run these on the ONS laptop, connected to the VPN. Keep the IPs off Jira and Slack, and delete the temp files at the end.

**1. Get the ONS VPN IPs from the Cloud Armor allow-list**

```sh
gcloud secrets versions access latest \
  --secret=cloud_armor_ip_allow_list \
  --location=europe-west2 \
  --project=ons-cicd-surveyassist
```

Note the three ONS VPN IPs.

**2. Read the current GKE allow-list for each environment**

```sh
gcloud secrets versions access latest \
  --secret=sandbox-gke-master-whitelist-cidrs \
  --project=ons-cicd-surveyassist > sandbox-cidrs.json

gcloud secrets versions access latest \
  --secret=preprod-gke-master-whitelist-cidrs \
  --project=ons-cicd-surveyassist > preprod-cidrs.json
```

Each file is a JSON list of entries like `{"display_name": "...", "cidr_block": "x.x.x.x/32"}`.

**3. Add the three VPN IPs to each file**

Keep the existing entries and add one entry per VPN IP. GKE needs CIDR format, so add `/32` to each IP. For example:

```json
{"display_name": "ons-vpn-1", "cidr_block": "<VPN_IP_1>/32"}
```

Check the files are still valid JSON:

```sh
jq . sandbox-cidrs.json
jq . preprod-cidrs.json
```

**4. Add a new version of each secret**

```sh
gcloud secrets versions add sandbox-gke-master-whitelist-cidrs \
  --project=ons-cicd-surveyassist --data-file=sandbox-cidrs.json

gcloud secrets versions add preprod-gke-master-whitelist-cidrs \
  --project=ons-cicd-surveyassist --data-file=preprod-cidrs.json
```

The old version stays, so it's easy to roll back by disabling the new one.

**5. Plan and apply Terraform, sandbox first**

```sh
cd survey-assist-sandbox
terraform init
terraform plan
```

Expected: one in-place change to `module.vector-store-gke.google_container_cluster.survey-assist-cluster`, adding the three entries under `master_authorized_networks_config`. It doesn't recreate the cluster, and the pods keep running.

If the plan shows other, unrelated changes, stop and check with Dan before applying. If needed, limit it to the cluster:

```sh
terraform plan -target=module.vector-store-gke.google_container_cluster.survey-assist-cluster
```

Apply once the plan looks right. Then repeat in `ons-survey-assist-preprod`, agreeing with Dan who applies preprod.

**6. Check it works**

Connect to each cluster from an ONS laptop on the VPN. See "How to test" at the bottom.

**7. Tidy up**

```sh
rm sandbox-cidrs.json preprod-cidrs.json
```

## How to test (connecting to the cluster)

**1. One-off setup**

You need `kubectl` and the GKE auth plugin:

```sh
gcloud components install kubectl gke-gcloud-auth-plugin
```

If gcloud components are locked down on the laptop, use `brew install kubectl` and ask for the plugin to be installed. Check both:

```sh
kubectl version --client
gke-gcloud-auth-plugin --version
```

**2. Connect to the VPN and log in**

```sh
gcloud auth login
gcloud config set project survey-assist-sandbox
```

**3. Get the cluster credentials**

This sets up your `kubectl` context to use the cluster's public endpoint, which is the one the allow-list protects.

```sh
gcloud container clusters get-credentials survey-assist-sandbox-cluster \
  --region=europe-west2 --project=survey-assist-sandbox
```

**4. Check you're pointing at the right cluster**

```sh
kubectl config current-context
```

You should see `gke_survey-assist-sandbox_europe-west2_survey-assist-sandbox-cluster`.

**5. Test the connection**

```sh
kubectl get --raw=/version
kubectl get nodes
kubectl get pods -n vector-store
```

- **Pass:** you see the version, the node list and the SAYT pods.
- **Blocked by the allow-list:** the command hangs, then times out (for example `dial tcp ... i/o timeout`). Check you're on the VPN and that step 5 of the main steps was applied.
- **Blocked by IAM:** you get `Forbidden`. That's a permissions issue, not the allow-list.

**6. Optional: prove the allow-list blocks you off the VPN**

Disconnect from the VPN and run `kubectl get nodes` again. It should time out.

**7. Repeat for preprod**

```sh
gcloud container clusters get-credentials ons-survey-assist-preprod-cluster \
  --region=europe-west2 --project=ons-survey-assist-preprod
kubectl config current-context
kubectl get nodes
kubectl get pods -n vector-store
```

Here's the flow for both cases. My read is that Cisco is re-signing the traffic. That fits the DNS workaround working, but it's not confirmed until we see the `openssl` issuer.

```
CASE 1: IP endpoint (what SA-1241 is for)  ->  FAILS

 ONS Mac            ONS VPN         Cisco web security            GKE control plane
 (kubectl)  ----->  tunnel  ----->  opens the TLS traffic  -----> public IP
                                    and re-signs it with           (allow-list: VPN IP OK)
                                    a Cisco certificate
     ^                                     |
     |_____________________________________|
   kubectl only trusts the cluster's own certificate.
   It gets Cisco's instead, so it says
   "x509: certificate signed by unknown authority" and stops.


CASE 2: DNS endpoint (workaround)  ->  WORKS

 ONS Mac            ONS VPN         Cisco web security            GKE DNS endpoint
 (kubectl)  ----->  tunnel  ----->  re-signs it the same  ------> (Google cert, IAM check)
                                    way
     ^                                     |
     |_____________________________________|
   kubectl checks against the Mac's keychain, which already
   trusts Cisco (Jamf installs it), so the connection is accepted.
   But this route only checks IAM. It ignores the IP allow-list,
   so it doesn't prove SA-1241.
```

**What to ask for, in plain English:** the ONS laptop's security software opens our secure connection to the cluster and re-signs it. kubectl sees a certificate it doesn't recognise and refuses to connect. We need ONS IT to tell that software to leave traffic to the GKE control plane IPs alone, so it passes through untouched. That's the "SSL inspection bypass".
