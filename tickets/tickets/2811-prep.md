| # | Benchmark | What it measures | Suggested target | Why it matters / what it proves | Test case |
|---|---|---|---|---|---|
| B1 | Concurrent users | Users actively going through the survey at the same time | 25 minimum, 50 target (agreed) | The system copes with the expected peak during the public test | Realistic 25, Realistic 50 |
| B2 | Journey completion rate | % of Locust journeys that finish start to end | 99% or more | People can actually finish a survey under load, not just load pages | Realistic 25 and 50 |
| B3 | Error rate | 5xx responses as a % of all requests | Under 1%, and no Cloud Armor blocks of test traffic | Failures stay rare, and the test isn't being blocked by our own WAF | All runs |
| B4 | Page latency (p95) | Time to load each UI page, for 95% of requests | Under 2 seconds per page | Pages feel responsive for nearly everyone, not just on average | Realistic 25 and 50 |
| B5 | Search-as-you-type latency (p95) | Time from a keystroke request to suggestions coming back (UI to API to vector store) | Under 1 second end to end | SAYT keeps up with typing. If it lags, the new UI feels broken | Realistic 50, vector store on its own |
| B6 | Throughput | Requests per second handled at a steady state | Record it, and compare to Ethan's ~22 req/s for the vector store on its own | Shows the headroom per component, and which one runs out first | Stress, vector store on its own |
| B7 | Breaking point | Users at which p95 latency or the error rate passes its limit | At least 2× the realistic peak (about 100 users) | Gives a safety margin if the public test is busier than expected | Stress (zero think time) |
| B8 | Scale-up behaviour | Time for Cloud Run instances and GKE pods to come up as load rises, and errors while they do | No error spike while scaling. Time the new SAYT pod start (8 GB image, model download, 25-second startup probe) | Spikes are handled without users seeing errors. Tells us if min instances or replicas need raising | Ramp up in Realistic 50 and Stress |
| B9 | Resource use | CPU and memory per Cloud Run instance and per pod | Under about 70% at 50 users | Right-sized with headroom. Feeds the pre-prod sizing and cost (SA-1279) | Realistic 50 |
| B10 | LLM quota | Vertex AI or Gemini calls per journey, and any 429s | No 429s at 50 users | Quota won't cap us in the public test. Gives the cost per run | Realistic 50, Stress |
| B11 | Recovery | Time to get back to normal latency after the stress run | Under 5 minutes, with no manual restarts, OOM kills or pod restarts | The system heals itself after a spike | After Stress |
| B12 | Stability over time (optional) | Latency, memory and errors over a long steady run | Flat for 60 minutes at 25 users | The public test runs for weeks. Catches memory leaks and slow build-ups that short runs miss | Soak (new, to propose) |

## Concerns to raise

- **The starting point may change.** Stand-up suggested scaling sandbox to last year's PFR settings first, rather than testing sandbox as it is. I need those settings, and Geoff may know them.
- **The vector store is new.** Last year's suite never ran against GKE. Pod start is slow (8 GB image, model download), the startup probe allows about 25 seconds, and the HPA timings are set for testing. It's the most likely new bottleneck.
- **Cloud Armor is changing.** Dan is upgrading the WAF rules in sandbox. The new rules could block Locust traffic or skew the results, so the runs need to happen with the rules we'll actually use.
- **Where Locust runs from.** A laptop on the ONS network goes through Cisco, with an unknown exit IP. A GCP VM or Cloud Run job gives a fixed IP to allow-list, and more capacity.
- **Access codes in pre-prod.** Making a new batch wipes the testers' codes. We need a plan before the final run.
- **Sandbox doesn't fully match pre-prod.** Some versions differ (for example the OTP service), so sandbox results are a guide, not proof. That's why the final run is in pre-prod.
- **Timing.** Sandbox is protected from GKE upgrades from 25 November to 9 December. If the runs slip past that, I'll extend it. Pre-prod needs its own dates (SA-1266).
- **Pre-prod is moving.** Dan and Rupert are pushing a new release to pre-prod. The final run needs a stable, recorded set of versions.
- **Handover.** Geoff leaves in early December. Agree what he hands over and who I go to after.
